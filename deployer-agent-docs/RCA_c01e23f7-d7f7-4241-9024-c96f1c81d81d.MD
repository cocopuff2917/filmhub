# RCA — filmhub-918: prod images 404 ("File not found")

## Symptom
- Prod `GET /api/files/cineverse/uploads/admin/69fd6623-df26-485a-9466-f168e4feb2aa.jpeg` → **404** `{"detail":"File not found"}` (reproduced on the live deployment).
- Same path in preview → 200 (image bytes), per reporter.

## Evidence gathered
- Deployment `filmhub-918`, active run `c01e23f7-d7f7-4241-9024-c96f1c81d81d`, status success, app healthy. Template `fastapi_react_mongo_shadcn_base_image`, frontend_type cloudflare.
- Prod DB (`filmhub-918-test_database`) `files` collection: **449 documents**. The exact cited record EXISTS: `storage_path = cineverse/uploads/admin/69fd6623-df26-485a-9466-f168e4feb2aa.jpeg`, content_type image/jpeg, size 12100, created 2026-10-05.
- Prod secrets: `EMERGENT_LLM_KEY` present & non-empty; `INTEGRATION_PROXY_URL` present, non-empty, and equals canonical `https://integrations.emergentagent.com` (verified via matches_expected=true).

## Root cause
Emergent Object Storage objects are stored in a namespace keyed by the `storage_key` that `init_storage()` derives from `EMERGENT_LLM_KEY`. The deploy pipeline's Mongo migration copied the `files` *metadata* into prod, but there is **no replication of the stored object bytes** from the preview storage namespace to the prod one. Because prod runs with a different `EMERGENT_LLM_KEY` than preview (standard platform behavior — prod is provisioned its own key), `init_storage()` in prod resolves to a different, effectively empty bucket. Hence every preview-uploaded object 404s in prod while its DB metadata is present.

`INTEGRATION_PROXY_URL` is correctly set to the shared integrations service and is NOT a contributing factor — the storage *service* is the same for both environments; only the per-key *namespace* differs.

## What could NOT be verified from the deployer toolset
- A literal value comparison of `EMERGENT_LLM_KEY` across preview vs prod. This toolset only reads the live prod run's secrets and never reveals values. To get a definitive yes/no, read preview `backend/.env` `EMERGENT_LLM_KEY` and compare (the deployer can confirm a match via `matches_expected` without exposing the value).

## Fix paths (choose one)
1. **Share the bucket** — In Deployment Panel → Secrets, set prod `EMERGENT_LLM_KEY` to the EXACT preview value, Save, then redeploy. `init_storage()` then resolves to the same namespace and all preview-uploaded objects become readable in prod. CAUTION: `EMERGENT_LLM_KEY` also identifies LLM usage/billing; sharing it couples preview and prod under one key.
2. **Re-populate prod storage** — Re-upload the images through the production admin UI so the bytes land in prod's own namespace. There is no automatic preview→prod object-byte copy and no DB-Manager-equivalent for object storage.

## Not a code bug
The backend storage code is correct; this is an environment/namespace + data-locality issue. No source change resolves it.
