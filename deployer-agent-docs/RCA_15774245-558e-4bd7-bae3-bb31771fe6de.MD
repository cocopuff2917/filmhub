# RCA — Actor photo thumbnails 404 on production (filmhub-918)

## Problem statement
Every image URL on prod (`https://filmhub-918.emergent.host`) returns 404, e.g.
`GET /api/files/cineverse/uploads/admin/69fd6623-...jpeg` → 404, body `{"detail":"File not found"}`, ~2.5–3.1s latency. Started after switching backend object storage to AWS S3 (primary) with Emergent storage as fallback. Reporter asked to confirm whether the AWS/storage secrets exist in LIVE PROD.

## Direct answer — production secrets (active run 15774245, names only, values never revealed)
All five keys EXIST in production and are non-empty:
- STORAGE_PROVIDER → **YES** (present, non-empty, matches_expected=`aws`)
- S3_BUCKET → **YES** (present, non-empty, matches_expected=`filmhub2026`)
- AWS_REGION → **YES** (present, non-empty, matches_expected=`us-east-1`)
- AWS_ACCESS_KEY_ID → **YES** (present, non-empty, matches_expected=`AKIAW4LWNEIHFC7K3ULN`)
- AWS_SECRET_ACCESS_KEY → **YES present, non-empty — but VALUE UNVERIFIED** (the expected value was redacted to me, so I could not compare it; `list_secrets` never returns values).

=> The "keys are missing from prod" hypothesis is **disproven**. The user does NOT need to ADD these keys; they are already present and 4 of 5 match the working preview values exactly.

## Evidence
- `list_secrets` on active run 15774245: all 5 keys present, non-empty; STORAGE_PROVIDER/S3_BUCKET/AWS_REGION/AWS_ACCESS_KEY_ID all `matches_expected=true`.
- `fetch_app_logs`: backend log line `botocore.credentials - INFO - Found credentials in environment variables` → boto3 does load AWS creds at runtime. Request log: `GET /api/files/...jpeg?format=thumbnail 404 Not Found`.
- `preview_health_check` on the failing path: 404, `{"detail":"File not found"}`, 3114 ms.
- Source (`backend/server.py`, read in eph sandbox from this run's source):
  - `get_object()` with `STORAGE_PROVIDER=="aws"` → `s3.get_object(Bucket=S3_BUCKET, Key=path)`; on ANY exception it calls `_get_from_emergent(path)` (legacy Emergent bucket); if that also returns None it re-raises.
  - `download_file()` catches the exception and returns `HTTPException(404, "File not found")`.
  - Config resolves from env exactly as prod provides it: `S3_BUCKET=os.environ["S3_BUCKET"]`, `S3_REGION=os.environ["AWS_REGION"]`, creds via boto3 default chain.
  - The ~3s latency is consistent with: S3 lookup attempted and failed → Emergent fallback attempted and failed → 404.

## Root cause
The 404 is NOT a missing-secret problem — all keys are present. The object is not retrievable in production via EITHER path: the S3 `get_object` raised and the Emergent fallback also returned nothing. Preview works with the same bucket/keys, so production differs in exactly one of two ways (I could not fully disambiguate with available tools):

1. **AWS_SECRET_ACCESS_KEY value in prod is stale/mismatched** vs the working preview value. This is the one secret I could not verify. A wrong secret → S3 auth error (InvalidAccessKeyId/SignatureDoesNotMatch) → exception → fallback → 404. This is the single most likely prod-only differentiator, since the other 4 values match preview exactly and preview serves the same objects from the same bucket.
2. **The object binaries were never migrated into the S3 bucket `filmhub2026`** under the referenced keys (DB references migrated, binaries did not). Production's Emergent fallback namespace does not contain the legacy preview objects either, so the fallback 404s too.

I cannot read the S3 bucket contents or compare the AWS_SECRET_ACCESS_KEY value (no value access / no S3 read tool), so both remain candidate causes — but secrets being *absent* is ruled out.

## Suggested fixes
- USER (Secrets): In Deployment Panel → Re-publish → Secrets → View & Edit, re-enter/confirm **AWS_SECRET_ACCESS_KEY** so it exactly matches the value that works in preview, then redeploy. (The other 4 keys are confirmed correct — do not change them.)
- USER (verify in AWS): Confirm the object actually exists in S3 bucket `filmhub2026` at key `cineverse/uploads/admin/69fd6623-df26-485a-9466-f168e4feb2aa.jpeg`. If it is NOT there, the image binaries were never migrated into the S3 bucket — upload/migrate them (DB references are already present). This is a data-migration gap, not a secrets gap.
